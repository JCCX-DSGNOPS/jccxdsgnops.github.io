Architecture

Token layers

NODO uses a two-layer variable architecture:

  • Primitives — Raw values: color ramps (neutrals, purple, blue, skyblue, red, green, yellow, orange), spacing scale, radius scale.
  • Semantic Tokens — Purpose-driven aliases: spacing/horizontal/inside-screen, radius/card, stroke/1. These reference primitives and provide context-aware naming.

Component hierarchy

NODO components follow atomic design principles:

  • Atoms — Basic elements: badges, buttons, chips, dividers, icons, switches, labels, status indicators.
  • Molecules — Functional groups: text fields, dropdowns, search, selectors, sliders, pagination, controls.
  • Organisms — Complex structures: cards, list items, navigation bars, banners, modals, sheets, charts, trackers.
  • Templates — Full-screen layouts: confirmation, error, invoice, onboarding, success, splash, loading screens.

Usage guidelines

Do

  • Use semantic tokens over raw color values
  • Maintain WCAG 2.1 AA contrast ratios (4.5:1 for text)
  • Use neutrals/10-30 for backgrounds, 60-100 for text
  • Reserve brand purple for primary actions and accents

Don't

  • Don't hardcode hex values; always bind to variables
  • Don't use more than 3 color families per screen
  • Don't use light text on light backgrounds
  • Don't use brand colors for error or warning states

Typography

Typography in NODO establishes visual hierarchy and readability across all components and screens.

Type scale

Principles

  • Legibility first — Minimum 12px for body text, 10px for captions and labels.
  • Consistent hierarchy — Use weight and size to differentiate heading levels, not color alone.
  • Line limits — Most component labels have a 2-line maximum to preserve layout integrity.
  • Truncation — Use ellipsis for overflowing text in constrained containers like cards and list items.

Guidelines

Do

  • Use text styles from the library consistently
  • Keep label text concise (2-line max for most components)
  • Use bold weight for emphasis, not underline or ALL CAPS
  • Maintain consistent line-height ratios

Don't

  • Don't mix custom font sizes with token values
  • Don't use more than 3 font weights per screen
  • Don't use colored text for emphasis (use weight instead)
  • Don't center-align long paragraphs

Layout patterns

Screen structure

Every NODO screen follows a consistent vertical structure:

  • Navigation bar — Fixed at top (root-navbar, flow-navbar, hero-navbar variants)
  • Content area — Scrollable, with spacing/vertical/below-header gap from nav
  • Sections — Separated by spacing/vertical/between-sections
  • Docked buttons — Fixed at bottom when present, with spacing/vertical/docked-buttons
  • Bottom bar — Global navigation at the very bottom

Iconography

Icons in NODO serve as visual cues that reinforce meaning and aid navigation. They are used across buttons, navigation, list items, and status indicators.

Guidelines

  • Icons should always be paired with labels in primary navigation
  • Use consistent stroke weight across all icons
  • Touch target minimum: 44x44px for interactive icons
  • Use semantic color tokens for icon fills (not hardcoded values)
  • Many NODO components have icon slots (buttons, list items, badges, navigation bars)

Design Principles

The foundational principles that guide every design decision in NODO.

1. Clarity over complexity

Every element must justify its presence. Prefer progressive disclosure (accordions, sheets) over information overload. Components like modals and fullscreen templates provide focused experiences for critical flows.

2. Consistency breeds familiarity

Reuse existing patterns before inventing new ones. NODO's 42 component categories cover most UI needs. Use the same component for the same purpose—don't mix banners and snackbars for similar notifications.

3. Hierarchy through restraint

Use one primary action per screen (one primary button). Create hierarchy through spacing and weight, not through excessive color or decoration. The docked-buttons pattern anchors the primary CTA.

4. Accessibility is non-negotiable

Every component must meet WCAG 2.1 AA standards. Touch targets must be at least 44px. Color must never be the sole indicator of state. All interactive elements need visible focus states.

5. Mobile-first, always

NODO is designed for mobile-first experiences. Components are sized for touch interaction. Layout tokens define mobile screen structure. Templates provide full-screen mobile patterns.

Accessibility

Building inclusive products with NODO. Every component is designed to support screen readers, keyboard navigation, and reduced motion preferences.

Color & Contrast

  • Maintain minimum 4.5:1 contrast ratio for normal text (WCAG AA)
  • Maintain minimum 3:1 for large text and UI elements
  • Badge component has an is-partel variant for ensuring contrast on different backgrounds
  • Never use color as the sole indicator of state; pair with icons or text

Touch targets

  • Minimum 44x44px touch target for all interactive elements
  • Buttons have 4 sizes: small (24px), medium (32px), large (40px), xlarge (48px)
  • Bottom bar items include adequate tap areas
  • Slider handlers must be easily graspable

Screen reader support

  • All interactive components should have descriptive labels
  • Decorative icons should be hidden from screen readers
  • Status changes (loaders, progress bars, snackbars) should be announced
  • Modal focus should be trapped within the modal when open

Interaction Patterns

Standard interaction patterns in NODO that ensure predictable and intuitive user experiences.

Feedback & confirmation

  • Snackbar — Temporary feedback for completed actions. Dismisses automatically. Use for non-critical confirmations.
  • Banner — Persistent messages that require acknowledgment. Use for warnings and system states.
  • Fullscreen confirmation — For critical success states (payment complete, transfer done). Use template-confirmation.
  • Error states — Use template-error-fullscreen for critical errors, empty-error-state for empty/error content areas.

Navigation patterns

  • Root navigation — root-navbar + bottom_bar_standard for main app sections.
  • Flow navigation — flow-navbar with back button for linear flows. Use stepper for multi-step processes.
  • Search — Use flow-navbar-search for search-first views.
  • Tabs — For switching between related views within the same context.

Data input patterns

  • Text fields — Use text-field for single-line, text-area for multi-line input.
  • Selection — dropdown for single selection from many options, selector for 2-4 options, chip for multi-select tags.
  • Controls — switch for on/off toggles, check-radio for multi-select/single-select lists.
  • OTP — Use input-otp for verification code entry.

Progressive disclosure

  • Accordion — For FAQ and settings sections. Only one open at a time in accordion-group.
  • Bottom sheets — handle-sheets for swipeable contextual content.
  • Modals — full-screen (modal) for focused tasks that block the main view.
  • Tooltip/Coachmark — For contextual help and onboarding hints.

Content Guidelines

Writing patterns and content principles for NODO components.

Labels & buttons

  • Use action verbs for buttons: "Confirmar", "Enviar", "Continuar"
  • Keep button labels to 1-2 words when possible
  • Use sentence case, not TITLE CASE
  • Destructive actions: use clear, specific labels ("Eliminar cuenta", not just "Eliminar")

Error messages

  • Tell the user what happened, why, and how to fix it
  • Avoid technical jargon
  • Use empty-error-state for recoverable empty states
  • Use template-error-fullscreen for critical failures

Amounts & numbers

  • Use label-amount for monetary values with consistent formatting
  • Use label-percentage for percentage displays
  • Badge numbers: show "99+" for values exceeding 99
  • Amounts in balance cards follow locale-specific formatting
